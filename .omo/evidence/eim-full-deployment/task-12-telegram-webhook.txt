4. IAM / AUTHENTICATION BLOCKERS
===============================================================================

DIRECT ENDPOINT TEST:
  curl -X POST https://telegram-bridge-7825647401.us-central1.run.app/webhook
    -H "Content-Type: application/json"
    -d '{"update_id":999999,"message":{...}}'
  
  Result: HTTP 403 Forbidden
  Body: <html><h1>Error: Forbidden</h1>
        "Your client does not have permission to get URL /webhook from this server."

IAM BINDING ATTEMPT:
  Command: gcloud run services add-iam-policy-binding telegram-bridge
             --member=allUsers --role=roles/run.invoker
  
  Result: FAILED_PRECONDITION
  Error: "One or more users named in the policy do not belong to a
          permitted customer, perhaps due to an organization policy."

ROOT CAUSE:
  Organization policy constraint: iam.allowedPolicyMemberDomains
  This prevents adding 'allUsers' (and likely 'allAuthenticatedUsers')
  to IAM policies in the aissc-core-engine-self-dep project.

  Without allUsers IAM binding, Cloud Run IAP rejects all
  unauthenticated requests with HTTP 403.

DEPLOY --allow-unauthenticated ATTEMPT:
  The --allow-unauthenticated flag was accepted by gcloud run deploy
  but the IAM policy setting step failed (same org policy constraint).
  Service deployed normally but remains authenticated-only.

BETA/ALPHA COMPONENTS:
  gcloud beta / gcloud alpha commands require component installation
  which is blocked in non-interactive sessions (prompt requires 'yes').
  Even if beta were installed, the same org policy would block the
  allUsers binding.

6. WORKAROUNDS & RESOLUTION PATHS
===============================================================================

OPTION A: Org Policy Exception (RECOMMENDED)
  Contact GCP org admin to relax iam.allowedPolicyMemberDomains for the
  aissc-core-engine-self-dep project, OR add an exception for the
  telegram-bridge service specifically.

  Once relaxed, this command would work:
    gcloud run services add-iam-policy-binding telegram-bridge \
      --region=us-central1 \
      --project=aissc-core-engine-self-dep \
      --member=allUsers \
      --role=roles/run.invoker

  Note: The service already has ingress=all, so once the IAM binding
  is in place, Telegram webhooks will flow through immediately.

  Use a Cloudflare Tunnel to expose the telegram-bridge service
  publicly via a CF-managed domain. CF Tunnel terminates at the
  cloudflared connector inside the VPC, bypassing GCP IAP entirely.

  Known CF resources available:
    - Cloudflare Account ID: 197a5689d9c0df2855f017dcbfc59f4a
    - CF API Tokens: multiple (cfat_*)
    - Existing Tunnel: clawdash
    - Would need: new Tunnel or Tunnel route, public hostname pointing
      to http://telegram-bridge-wp6tii27hq-uc.a.run.app:443 or
      the internal Cloud Run endpoint

  Then: register webhook to the CF-managed domain instead of the
  run.app URL.

OPTION C: Polling Mode (FALLBACK, NO INFRA CHANGE)
  Switch the telegram-bridge from webhook mode to long-polling mode
  using Telegram's getUpdates API. This would require changes to
  telegram-bridge/main.py (or a companion process) to poll
  continuously, but requires ZERO infra/org policy changes.

  This is the fastest workaround if the org exception is delayed.
